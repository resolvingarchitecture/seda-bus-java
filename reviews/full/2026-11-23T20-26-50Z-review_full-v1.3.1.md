## Summary

27 things need attention now, and 13 of 21 recorded stakeholder needs are not fully answered by the design. 56 further improvements follow. Review readiness: HIGH_CONFIDENCE.

## Needs Attention Now

The 7 most serious of 27 high-severity problems; the others are first under Other Improvements. Tick each off as it is fixed.

- [ ] **Implementation differs from the design: Three delivery levels with file persistence and ExactlyOnce dedup.** SEDAMessageChannel: dedup set in memory only; ack before forward; envelope-level guaranteed level on an AtMostOnce channel is not persisted. **Fix:** Persist dedup, ack after forward, and honour the envelope-level ServiceLevel for persistence.
- [ ] **Implementation differs from the design: Integration failure handling: back-pressure, bounded retry, dead-letter.** deadLetter() returns false when channelDir is null (AtMostOnce channels); process() ignores this, so the envelope is lost. **Fix:** Provide dead-letter handling for all levels, or report the loss.
- [ ] **Implementation differs from the design: NFR: zero loss after crash, ordered replay, dedup.** No replay test; the delivered set is not persisted; the completed() forward result is ignored after ack. **Fix:** Fix and add crash-replay tests.
- [ ] **Implementation differs from the design: NFR: event-driven drain, lock-free hot path.** Drain is event-driven, but ArrayBlockingQueue, the synchronized consumer snapshot and the dedup map lock on every envelope. **Fix:** Correct the NFR wording or the implementation.
- [ ] **The public surface is explicit and the rest is internal.** registerChannel returns a full MessageChannel; calling send() on it bypasses pool.schedule; the public surface is not listed. **Fix:** Document the supported public API and make channel send() trigger scheduling, or return a restricted view.
- [ ] **The public contract is documented.** Javadoc covers delivery levels but not thread-safety, nullability, errors or ordering of public operations. **Fix:** Document each public SEDABus operation's inputs, results, errors, threading and ordering.
- [ ] **A versioning and compatibility policy exists.** Version 1.3.1 in the pom; no versioning or deprecation policy recorded. **Fix:** Adopt semver with a stated definition of breaking change and a deprecation window.

## Other Improvements

**More high-severity problems**

- [ ] Lifecycle is defined, including what happens to work in flight. Fix restart, make the lifecycle idempotent, and document what happens to queued and in-flight work.
- [ ] Which calls may block is stated, and blocking cannot exhaust the worker pool. Never block on pool threads; use offer with timeout or reject, and document handler threads.
- [ ] Every queue, buffer, cache and map is bounded, with a stated policy at the limit. Remove the callback and notify failure on dead-letter or drop, and bound the map.
- [ ] Failure modes are listed for each operation. Add a failure-mode table per public operation.
- [ ] No failure is silent. Keep an in-memory or hooked dead-letter for all levels and handle every ignored result.
- [ ] Delivery guarantees match the implementation. Ack only after the next hop accepts, or dead-letter on forward failure.
- [ ] Deduplication state is as durable as the guarantee it supports. Persist delivered ids, for example by appending to a file, or downgrade the ExactlyOnce claim.
- [ ] Failure paths and concurrency are tested, and time and I/O can be faked. Add replay and crash-mid-write tests and inject a clock and file store.
- [ ] Documentation matches the code. Reconcile documentation and code for each listed contradiction.
- [ ] The project can continue if its owner is unavailable. Document build and release steps and share access.
- [ ] Message integration has retry and dead-letter handling. Provide dead-letter handling for every service level.
- [ ] Contracts are machine-readable and tested. Create shared conformance tests for MessageBus semantics.
- [ ] Change follows compatibility rules. Adopt additive-only change rules and a deprecation window.
- [ ] Delivery semantics and ordering are stated for each channel. Add per-channel ordering guarantees alongside the delivery levels.
- [ ] Exactly-once claims hold end to end. Persist dedup state and track per-subscriber fan-out success.
- [ ] Sibling implementations are held in step by a conformance suite. Publish shared language-neutral test vectors run by every port.
- [ ] Handler failure is part of the contract. Document handler blocking and re-entrancy rules.
- [ ] Complexity does not exceed team capacity. Automate parity checks to keep the load within one person's capacity.
- [ ] Dependencies are scanned and listed. Add CycloneDX SBOM generation and dependency scanning to the build.
- [ ] Releases are signed and their integrity can be checked. Sign releases (GPG/Sigstore) when publishing to a real repository.

**Structure and boundaries**

- [ ] Layers or packages and the allowed dependency direction are stated. State that channel depends on bus only through a completion interface, and that pool depends on channel only.
- [ ] Component dependencies are acyclic, or each cycle is a recorded decision. dependency cycle: sedabus → sedamessagechannel → workerthreadpool → sedabus.
- [ ] Components are cohesive and of reasonable size. Extract an EnvelopeStore (persist/replay/dead-letter) and a delivery policy from the channel.

**Contracts and API**

- [ ] Failures are reported in one consistent way. Define one failure channel, such as a boolean result plus a failure listener, and apply it everywhere.
- [ ] Configuration is documented, validated and safe by default. Document every property with its default and range, and expose maxAttempts.

**Concurrency and state**

- [ ] Ordering guarantees are stated, and so is where they stop. Document per-channel ordering and what breaks it.
- [ ] Long operations have timeouts and can be cancelled. Add a configurable send timeout for Block.

**Failure handling**

- [ ] Every external or handler call has a timeout. Document the handler contract and optionally enforce a handler timeout.

**Persistence in the application**

- [ ] On-disk and wire formats are documented and versioned. Document the file format, add a version field, and define a migration approach.

**Quality, testing and evolution**

- [ ] Performance claims have a benchmark. Add a JMH publish/drain benchmark with recorded results.
- [ ] Observability is proportionate to the class. Add cheap per-channel counters and a failure listener (metrics hooks are on the roadmap).
- [ ] Compatibility is checked automatically for a library with dependents. Add japicmp against the previous release, failing on unannounced breaks.
- [ ] Change is easy where change is expected. Introduce a stage-policy interface for concurrency and retry delay.

**Security inside the application**

- [ ] Dependencies are few, pinned and scanned. Add OWASP dependency-check or an equivalent to the build.

**Decisions, build and documentation**

- [ ] The build is reproducible and the target is tested. Add CI running tests on JDK 11 and the latest LTS.
- [ ] Structural decisions are recorded with their alternatives. Add rejected alternatives to the key decisions.

**Application anti-patterns**

- [ ] Swallowed errors. Surface these failures to the caller or a failure hook.
- [ ] Busy waiting. Track in-flight work with a counter or latch instead of polling.

**Strategy and value**

- [ ] Business capabilities are identified and mapped. Name the capability (in-process staged messaging) and map the components to it.
- [ ] Build, buy or reuse is a decision for each major capability. Record the build-versus-reuse rationale.
- [ ] Cost, funding and total cost of ownership assumptions are stated. State the maintenance effort assumptions.
- [ ] A roadmap sequences the work and its dependencies. Sequence them, for example metrics hooks before the adaptive controller, and publishing before signing.

**Governance and decision rights**

- [ ] Stakeholder conflicts and priorities are resolved and recorded. Record which policies are permitted with guaranteed service levels.
- [ ] Architecture is reviewed on a cadence. Review on each minor release and on any cross-port change.

**Standards and portfolio**

- [ ] Shared components have a lifecycle and versioning. Define the release process and deprecation policy.
- [ ] Implementations in several languages are kept in step. Maintain a shared specification plus conformance vectors.
- [ ] Decommissioning and lifecycle are planned. Note an end-of-life approach and data cleanup.

**Ownership and accountability**

- [ ] Key-person risk is identified with a mitigation. Record the risk and a mitigation, such as a documented release process or a co-maintainer.

**Stage fit**

- [ ] Investment matches the stage. Prioritise the hard-to-change items: format versioning and API policy.
- [ ] The path to the next stage is planned. Define the 2.0 entry criteria and order.

**Provisioning and delivery**

- [ ] Builds and releases are automated. Add a CI workflow for build, test and release.

**Embedded runtime**

- [ ] Supported runtime versions are stated and tested. Run tests on JDK 11 and current LTS in CI.
- [ ] The resource footprint is documented and configurable. Document thread, memory and disk footprint and make dedup size configurable.

**Boundaries and contracts**
