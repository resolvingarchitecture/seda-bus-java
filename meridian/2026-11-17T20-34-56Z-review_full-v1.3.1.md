# Architecture Review

## Summary

17 things need attention now, and 0 of 21 recorded stakeholder needs are not fully answered by the design. 38 lower-priority improvements follow. Review readiness: HIGH_CONFIDENCE.

This review is limited by what was supplied: 21 checks could not run until some context is confirmed, and implementation evidence was not assessed. See *Improve the review* below.

## Needs Attention Now

These are the high-severity problems, most serious first.

1. **The public surface is explicit and the rest is internal.** No exported packages or public classes are listed beyond the MessageBus implementation. **Fix:** List the public API; hide the rest via module-info or package-private.
2. **The public contract is documented.** Inputs, errors, nullability, ordering and thread-safety of public operations are undocumented. **Fix:** Document each public operation's contract in Javadoc.
3. **A versioning and compatibility policy exists.** No versioning or deprecation policy is recorded, despite two downstream consumers and a planned 2.0. **Fix:** Adopt semver and define what counts as breaking.
4. **Lifecycle is defined, including what happens to work in flight.** No start, stop or close semantics or fate of queued work at shutdown is stated, though the library holds work. **Fix:** Define idempotent shutdown and the drain or persist behaviour.
5. **Which calls may block is stated, and blocking cannot exhaust the worker pool.** Handlers run on the shared pool; blocking handlers versus the sum of permits and pool size is not addressed. **Fix:** State handler threads and bound total permits to the pool size.
6. **Failure modes are listed for each operation.** Failure modes are given only for full queue and nack; persistence write failure and replay corruption are missing. **Fix:** Tabulate the failure modes per public operation.
7. **Deduplication state is as durable as the guarantee it supports.** Whether the bounded ExactlyOnce dedup history survives a crash is not stated. **Fix:** Persist the dedup ids with the envelope, or document the limitation.
8. **Failure paths and concurrency are tested, and time and I/O can be faked.** One test class; timing-based tests; no crash mid-write or file-system fault injection evidenced. **Fix:** Add an injectable clock and file system plus crash-injection tests.
9. **The project can continue if its owner is unavailable.** No documented build or release handover; a single owner holds all decisions. **Fix:** Write a release runbook and share access.
10. **Contracts are machine-readable and tested.** A Java interface exists, but no conformance or consumer tests are evidenced. **Fix:** Create a MessageBus conformance test suite.
11. **Change follows compatibility rules.** No compatibility or deprecation rules are recorded. **Fix:** State additive-only change and a deprecation window.
12. **Delivery semantics and ordering are stated for each channel.** Delivery level is per channel, but per-channel ordering under concurrency is unstated. **Fix:** State the ordering guarantee per channel.
13. **Sibling implementations are held in step by a conformance suite.** Seven ports are kept in lockstep with no shared test vectors. **Fix:** Publish cross-language conformance vectors.
14. **Handler failure is part of the contract.** Only nack is defined; handler throw, block and re-entrant publish behaviour is undefined. **Fix:** Specify the handler failure and re-entrancy contract.
15. **Complexity does not exceed team capacity.** One maintainer keeps seven language ports in lockstep. **Fix:** Reduce the lockstep burden with conformance vectors or add maintainers.
16. **Dependencies are scanned and listed.** No SBOM or vulnerability scanning is evidenced. **Fix:** Generate a CycloneDX SBOM and scan on each build.
17. **Releases are signed and their integrity can be checked.** jitpack builds; no signed artefacts for a foundational library. **Fix:** Publish signed artefacts to Maven Central.

## Other Improvements

**Structure and boundaries**

- Layers or packages and the allowed dependency direction are stated. Document packages and the permitted dependency direction.
- Component dependencies are acyclic, or each cycle is a recorded decision. dependency cycle: sedabus → sedamessagechannel → workerthreadpool → sedabus.
- Components are cohesive and of reasonable size. Extract persistence and retry/dead-letter policy collaborators.

**Contracts and API**

- Failures are reported in one consistent way. State and apply one failure-reporting mechanism.
- Configuration is documented, validated and safe by default. Document defaults and ranges; reject invalid values.

**Concurrency and state**

- Ordering guarantees are stated, and so is where they stop. Document per-channel ordering and what breaks it.
- Long operations have timeouts and can be cancelled. Add timeouts or cancellation to long operations.

**Failure handling**

- Every external or handler call has a timeout. Add an optional per-channel handler timeout.

**Persistence in the application**

- On-disk and wire formats are documented and versioned. Add a format version field and a migration note.

**Quality, testing and evolution**

- Performance claims have a benchmark. Add a JMH benchmark and record the results.
- Observability is proportionate to the class. Expose depth, retry and dead-letter counters and a failure listener.
- Compatibility is checked automatically for a library with dependents. Add japicmp to the build.
- Change is easy where change is expected. Introduce sizing and retry policy interfaces now.

**Security inside the application**

- Dependencies are few, pinned and scanned. Add OWASP dependency-check or an equivalent to the build.

**Decisions, build and documentation**

- The build is reproducible and the target is tested. Add CI that runs tests on JDK 11.
- Structural decisions are recorded with their alternatives. Add the rejected alternatives to key decisions.
- Releases are traceable. Tag releases and keep a CHANGELOG.

**Strategy and value**

- Build, buy or reuse is a decision for each major capability. Record the build-versus-reuse decision.
- A roadmap sequences the work and its dependencies. Sequence the work: CI, publishing, metrics, backoff, rotation, then the controller.

**Standards and portfolio**

- Shared components have a lifecycle and versioning. Define the release process and deprecation path.
- Implementations in several languages are kept in step. Maintain a shared specification and conformance suite.
- Decommissioning and lifecycle are planned. State end-of-life support and on-disk data cleanup.

**Ownership and accountability**

- Every component has an owning team or person and a support path. State the support channel.
- Key-person risk is identified with a mitigation. Record the risk and name a backup maintainer.

**Risk and compliance posture**

- Licensing and intellectual-property obligations are understood. Record the ra-common licence.

**Stage fit**

- Investment matches the stage. Prioritise publishing and the compatibility policy before 2.0.
- The path to the next stage is planned. Define 2.0 entry criteria.

**Provisioning and delivery**

- Builds and releases are automated. Add CI to build, test and release.

**Embedded runtime**

- Supported runtime versions are stated and tested. Add a CI JDK matrix (11, 17, 21).
- The resource footprint is documented and configurable. Document the footprint and how to configure it.

**Boundaries and contracts**

- Each integration has an API contract and a version. Document the MessageBus semantics in ra-common.
- Each external dependency has an owner. Record the ra-common owner.
- Producers and consumers of every integration are identified. Define change notification (changelog or release notes).

**Asynchronous and message integration**

- Backlog and lag are visible and bounded. Expose depth counters to the host.

**Operating integrations**

- A correlation id travels across every hop. State the envelope id as the correlation id in dead-letters and hooks.

**Monitoring and response**

- An incident response plan exists and has been exercised. Add a lightweight security response procedure.
- Vulnerabilities are disclosed and patched on a schedule. Add SECURITY.md with a contact and fix SLA.

**Governance and decision rights**

- Architecture is reviewed on a cadence. Review on each minor release or each cross-port change.
